# Scope Topic

## PMI Definition
Project scope defines the boundaries of the project - what is included and explicitly excluded. It describes the deliverables, features, and functionalities the project will produce, along with the work required to achieve them.

## What to Understand
- What's IN scope (core deliverables and features)
- What's OUT of scope (explicit exclusions)
- Key boundaries and limitations
- Acceptance criteria for deliverables
- Relationship to project goals

## What to Infer
From the user's description, infer:
- Implied scope boundaries from goals
- Natural exclusions based on timeline/budget
- Dependencies on external systems or teams
- Phase-based scope (MVP vs full release)
- Integration boundaries

## What to Probe (Only if Missing)
- "What are the must-haves versus nice-to-haves?"
- "Is there anything specifically NOT part of this project?"
- "What would be a v2 candidate if time runs short?"

## Intelligent Behaviors
- Distinguish between scope and requirements (scope = boundaries, requirements = specifics)
- Flag scope creep risks early
- Suggest out-of-scope items based on similar projects
- Connect scope decisions to budget/timeline impact
- Recommend documenting "explicitly out of scope" items

## Common Pitfalls to Flag
- Scope that's too broad for the timeline
- Missing "out of scope" documentation
- Scope that doesn't align with stated goals
- Unclear boundaries with adjacent systems
- "Everything is priority 1" syndrome

## Cross-Topic Dependencies
Consider scope in context of:
- **Goal**: Scope should directly support achieving goals
- **Requirements**: Scope defines the container for requirements
- **Budget/Schedule**: Scope must fit within constraints
