# Requirement Topic Insights

## Real-World Experience

### Do's
- Write requirements from user perspective, not developer perspective - "user can upload" not "system stores files"
- Include acceptance criteria for every requirement - "done" needs a definition
- Distinguish must-have from nice-to-have explicitly - use MoSCoW or similar
- Trace requirements to goals - if it doesn't serve a goal, question its priority
- Version requirements - they evolve, and you need to track changes

### Don'ts
- Don't accept solution specifications as requirements - "use microservices" isn't a need, it's a design choice
- Don't skip non-functional requirements - performance, security, accessibility matter
- Don't write requirements in isolation - involve users and developers in refinement
- Don't over-specify implementation details - leave room for good engineering decisions

### Warnings
- Requirements that everyone agrees on but no one can define clearly will cause rework
- "Common sense" requirements often aren't common - be explicit
- Requirements from executives often skip the middle layers who have to implement
- Late requirement changes are 10x more expensive than early changes

### Recovery Tips
- If requirements conflict, facilitate prioritization with the product owner - don't arbitrate yourself
- When requirements are unclear, build the simplest version and get feedback - iteration beats speculation
