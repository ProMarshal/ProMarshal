# Deliverable Topic Insights

## Real-World Experience

### Do's
- Define acceptance criteria before building - stakeholders and team should agree on "done"
- Include documentation as a deliverable - don't let it be an afterthought
- Plan for transition deliverables - training materials, runbooks, handoff docs
- Get formal sign-off on major deliverables - verbal acceptance is forgettable
- Version deliverables clearly - especially documents that evolve

### Don'ts
- Don't assume everyone shares your definition of quality - make standards explicit
- Don't skip interim deliverables - they create checkpoints and early feedback
- Don't deliver incomplete work and call it done - it erodes trust
- Don't forget intangible deliverables - trained users, updated processes, knowledge transfer

### Warnings
- Deliverables without owners often slip through the cracks
- The gap between "technically complete" and "user-ready" is often underestimated
- Documentation deliverables are often deprioritized and then rushed at the end
- Acceptance testing frequently reveals quality issues - plan time for fixes

### Recovery Tips
- If a deliverable fails acceptance, understand why before fixing - symptom vs. root cause
- When deliverable scope creeps, split it or negotiate a follow-up phase
