# Scope Topic Insights

## Real-World Experience

### Do's
- Document what's OUT of scope as thoroughly as what's IN - ambiguity here causes most scope creep
- Get scope sign-off in writing before any development starts - verbal agreements "evolve"
- Review scope with stakeholders at every milestone - catch drift early
- Create a "parking lot" for good ideas that aren't in this version - it validates the idea without committing to it
- Size scope relative to team and timeline - a 3-person team can't build what a 30-person team can

### Don'ts
- Never accept scope changes without assessing timeline and budget impact - free changes aren't free
- Don't assume adjacent features are included - explicitly list what "naturally" belongs with each feature
- Don't let anyone add scope verbally - make "email the PM" the price of admission
- Don't estimate scope you don't understand - get clarification before sizing

### Warnings
- Scope that's "obviously needed" but never written down will bite you at acceptance testing
- "Small" changes pile up - 20 small changes equal one big change in effort
- When the same stakeholder keeps asking for additions, have the priority conversation
- Scope creep often starts with "while you're in there anyway..." - this phrase is a red flag

### Recovery Tips
- If scope has exploded, force-rank all items and draw a line - everything below the line is v2
- When scope changes conflict, put them on a table with timeline/cost impact and let the owner decide
